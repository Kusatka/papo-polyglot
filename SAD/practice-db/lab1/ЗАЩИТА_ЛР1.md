# Защита лабораторной работы №1

**Тема:** аналитический запрос к распределённой структуре хранения через API Gateway с JWT.
**Что сдаётся:** `Отчёт_Лабораторная_1.docx` / `.pdf` и каталог `SAD\practice-db\lab1`.

Задание: 10 студентов с минимальным процентом посещения лекций, в которых встречается заданный
термин или фраза, за период обучения. В отчёте: полная карточка студента, процент посещения,
период, термин в занятиях курса.

Ключевая фраза, с которой стоит начать:

> «Запрос идёт в три хранилища, каждое делает то, что умеет лучше всего. Elasticsearch по фразе с
> русской морфологией находит лекции с термином — из 152 лекций остаётся 17. PostgreSQL по этим 17
> лекциям считает процент посещения за период прямо в СУБД, и благодаря недельным партициям читает
> только недели периода. Redis отдаёт карточки 10 студентов из кэша, а при промахе сервис берёт их из
> PostgreSQL и кладёт обратно с TTL. Снаружи доступен только шлюз: он выдаёт JWT и проверяет его на
> каждом вызове, а сервис проверяет подпись ещё раз.»

## 1. Подготовка

1. Запусти стенд ПР №1: в `pr1` выполни `docker compose up -d` и дождись `(healthy)` у всех.
   Данные ПР №3 уже лежат в томах. Если стенд пересоздавался, в `pr3` выполни `./load_all.sh`.
2. В каталоге `lab1` выполни:

```bash
docker compose up -d --build
```

Через 20–30 секунд `docker compose ps` покажет оба контейнера `(healthy)`.

3. Открой в браузере `http://localhost:8000/docs` (Swagger UI шлюза).
4. Открой отчёт на рисунке 2 (C4, контейнеры) и рисунке 4 (DFD уровня 1).

**Учётные записи шлюза (тестовые, только для локального стенда):** `teacher` / `teacher-pass`
и `student` / `student-pass`. В `.env` лежат только PBKDF2-хеши паролей, самих паролей там нет.
Новый хеш делается так:

```bash
docker exec api-gateway python -c "from app.common.security import hash_password; print(hash_password('новый-пароль'))"
```

## 3. Готовые команды (Windows PowerShell, каталог `lab1`)

```powershell
$B = "http://localhost:8000"
# без токена → 401
curl.exe -s -w "  [HTTP %{http_code}]`n" "$B/api/lab1/report?term=Kafka&date_from=2026-02-09&date_to=2026-04-19"
# вход и отчёт
$tok = (Invoke-RestMethod -Method Post "$B/auth/login" -Body @{username = 'teacher'; password = 'teacher-pass'}).access_token
$r = Invoke-RestMethod "$B/api/lab1/report?term=масштабирование&date_from=2026-02-09&date_to=2026-04-19&trace=true" -Headers @{Authorization = "Bearer $tok"}
$r.trace | Format-List step, store, action, result, ms
$r.students | Format-Table rank, @{n = "ФИО"; e = {$_.student.full_name}}, @{n = "Группа"; e = {$_.student.group}}, attended, total, attendance_pct -AutoSize
# что лежит в токене
curl.exe -s -H "Authorization: Bearer $tok" "$B/auth/me"
# обход шлюза: прямой вызов сервиса изнутри сети Docker без токена → 401
docker exec api-gateway python -c "import httpx; print(httpx.get('http://lab1:8001/report', params={'term': 'Kafka', 'date_from': '2026-02-09', 'date_to': '2026-04-19'}).status_code)"
# журнал шагов сервиса
docker logs --since 1m lab1-service
```

## 4. Вопросы и ответы

### Архитектура

**Зачем API Gateway?** Единая точка входа: аутентификация, проверка токена, маршрутизация к
сервисам лабораторных и документация API в одном месте. Сервисы лабораторных не публикуются наружу
и не дублируют логику входа. Следующие лабораторные добавляются новым маршрутом `/api/labN/...`.

**Почему у шлюза и сервиса один образ?** Код общий (модуль `app.common.security`), разница только
в команде запуска (`command` в compose). Образ собирается один раз (224 МБ), а контейнеры остаются
отдельными: их можно перезапускать, ограничивать и масштабировать независимо.

**Что такое C4 и какие уровни показаны?** Модель Саймона Брауна из четырёх уровней: контекст,
контейнеры, компоненты, код. В отчёте два верхних уровня. Контекст — система, люди и внешние
системы. Контейнеры — отдельно запускаемые части: приложения и базы данных.

**Чем нотация Йордана–Коуда отличается от Гейна–Сарсона?** У Йордана–Коуда (и Де Марко) процесс —
окружность, хранилище — две параллельные линии. У Гейна–Сарсона процесс — прямоугольник со
скруглёнными углами, хранилище — прямоугольник, открытый справа. Внешняя сущность в обеих —
прямоугольник. Контекстная диаграмма — один процесс 0. Уровень 1 раскрывает его, при этом потоки к
внешним сущностям сохраняются (балансировка уровней).

**Что будет, если упадёт Elasticsearch?** Сервис получит ошибку на шаге 1 и ответит 500, шлюз
вернёт 502 с текстом ошибки (раздел `except ValueError` в шлюзе). Отчёт без поиска по термину
построить нельзя, поэтому запасного пути нет. Это осознанное решение.

### Обоснование выборки

**Почему поиск в Elasticsearch, а не `ILIKE` в PostgreSQL?** Нужны словоформы: «очереди сообщений»
должно находить «Очередь сообщений». Анализатор `russian_custom` делает стемминг, `multi_match` с
`type: phrase` требует слова фразы подряд. Индекс уже построен в ПР №3. `ILIKE '%...%'` не знает
морфологии и читает все тексты. Кроме того, Elasticsearch сразу возвращает фрагмент с подсветкой —
это поле «термин в занятиях курса».

**Зачем `search_after`?** Обычный `size` ограничивает выдачу, а лекций с частым термином может быть
больше. Постраничный проход по сортировке `lecture_id` гарантирует, что в шаг 2 попадут все лекции.
`track_total_hits` даёт точное общее число, сервис пишет «найдено 17 из 17».

**Почему посещаемость считает PostgreSQL?** Журнал посещаемости — транзакционные данные, его полная
и точная копия есть только в PostgreSQL. Агрегат выполняется там, где лежат данные: в сервис
возвращаются 10 строк, а не 462 отметки.

**Как работает отсечение партиций?** `attendance` разбита `PARTITION BY RANGE (week_start_date)` на
недели. В запросе есть условие `week_start_date BETWEEN <понедельник первой недели> AND date_to`, и
планировщик не читает партиции вне диапазона. Точную границу по дням задаёт второе условие — на
`schedule.scheduled_date`.

**Как считается процент?** Посещённые лекции с термином / все лекции с термином, которые были у
группы студента в периоде × 100, с округлением до десятых. При равном проценте выше в списке тот, у
кого больше занятий (больше пропусков), затем порядок по id, чтобы результат был однозначным.

**Почему именно эти 10 студентов, а не другие с тем же процентом?** На границе (50 %) студентов с
одинаковым результатом больше, чем помещается в отчёт. Правило выбора явное и детерминированное
(`ORDER BY attendance_pct, total DESC, student_id`), прямой SQL в `verify.py` даёт тот же порядок.

**Зачем Redis, если карточки есть в PostgreSQL?** Карточки студентов читают часто, а меняются они
редко. В ПР №3 для них предусмотрен кэш `student:{id}` с TTL. Схема cache-aside: сначала кэш одним
конвейером `HGETALL`, недостающие карточки — одним запросом из PostgreSQL, затем запись в кэш с
`EXPIRE 7200`. На рисунке 12 время шага с промахами — 19,5 мс, из кэша — 1,3 мс.

**А если данные в кэше устарели?** Устаревание ограничено TTL (2 часа). В ЛР №4–6 изменения будут
приходить в Redis через CDC (Debezium → Kafka). Кэш на результат не влияет: даже пустой Redis даёт тот
же отчёт, только медленнее.

**Почему не MongoDB и не Neo4j?** Тексты лекций для поиска уже есть в Elasticsearch, а связь
«студент — занятие» однозначно задаёт журнал посещаемости. Обход графа или документ занятия этому
запросу ничего не дают, лишний шаг только добавил бы задержку.

**Почему не одним SQL-запросом?** Можно, но без морфологии и подсветки, с полным перебором текстов
лекций. Разделение даёт каждому шагу подходящий движок, а между шагами передаются только
идентификаторы (UUID v5 одинаковы во всех хранилищах).

### Безопасность и JWT

**Что такое JWT и что в нём лежит?** Три части в base64url через точки: заголовок (`alg: HS256`),
полезная нагрузка и подпись. У нас в нагрузке `sub` — логин, `role`, `iss` = papo-gateway, `iat` и
`exp` (60 минут). Содержимое не зашифровано, его может прочитать любой (`/auth/me`, jwt.io), но
изменить его без ключа нельзя: подпись не сойдётся (рисунок 7).

**HS256 или RS256?** HS256 — симметричная подпись одним секретом. Здесь подписывает и проверяет
одна доверенная сторона (шлюз и сервис из одного проекта), секрет лежит в `.env`. Если токены будут
проверять сторонние сервисы, лучше RS256: подпись закрытым ключом, проверка открытым.

**Зачем сервис проверяет токен второй раз?** Это эшелонированная защита. Если кто-то попадёт в сеть
Docker, вызвать сервис в обход шлюза без действительного токена он всё равно не сможет (рисунок 7,
пункт 9).

**Как хранятся пароли?** Только PBKDF2-SHA256 с 16-байтовой солью и 200 000 итераций. Сравнение — за
постоянное время (`hmac.compare_digest`), чтобы по времени ответа нельзя было подбирать хеш.

**Что если токен украдут?** Он действует не дольше 60 минут (`exp`). Отзыва токенов и refresh-токенов
нет. Для учебной работы этого достаточно, в промышленной системе добавили бы короткоживущий access-
и долгоживущий refresh-токен, а также чёрный список.

**Роли teacher и student чем-то различаются?** Сейчас — нет: роль записывается в токен, оба
пользователя могут вызвать отчёт. Разграничить доступ — одна проверка `user['role']` в методе
шлюза. Задание требует аутентификацию, а не авторизацию по ролям.

**Почему HTTP, а не HTTPS?** Стенд локальный. В эксплуатации TLS терминируется на шлюзе или на
обратном прокси перед ним. Внутренний вызов шлюз → сервис идёт по изолированной сети Docker.

### Тестирование

**Чем доказана правильность результата?** Тремя способами. Каждый шаг повторён напрямую в своём
хранилище (рисунки 10–12). Итог пересчитан независимым SQL-запросом без партиций и кэша, совпали все
10 строк для двух терминов (рисунок 13). Граничные случаи дают ожидаемые 401 и 422 и пустой отчёт
(рисунки 6, 7, 14).

**Что такое трассировка?** Параметр `trace=true` добавляет в ответ шаги исполнения: хранилище,
действие, результат и время. Те же строки пишутся в журнал контейнера (`docker logs lab1-service`).
Это и есть «последовательность исполнения с выводом результатов на каждом шаге» из задания.

## 5. Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| `curl: (7) Failed to connect ... 8000` | Шлюз не запущен: `docker compose up -d` в `lab1`. |
| 502 «Сервис ЛР №1 недоступен» | Сервис не стартовал или ещё не `healthy`: `docker compose ps`, `docker logs lab1-service`. |
| 500 / 502 на шаге 1 | Не запущен Elasticsearch или нет индекса `lectures`: стенд `pr1`, затем `./load_all.sh es` в `pr3`. |
| Пустой отчёт для любого термина | Нет данных в PostgreSQL: `./load_all.sh pg` в `pr3`. |
| Кириллица ломается в `curl.exe` | В URL пиши кириллицу через `Invoke-RestMethod` (как в разделе 3) или используй Swagger UI. |
| 401 «Срок действия токена истёк» | Прошло больше 60 минут: снова `Authorize` в Swagger или новый `$tok`. |
| Docker не запускается | Компьютер загружен в запись «без Hyper-V» (VirtualBox): перезагрузись в обычную Windows. |
