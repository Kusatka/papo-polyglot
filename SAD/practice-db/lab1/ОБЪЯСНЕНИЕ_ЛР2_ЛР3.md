# Реализация ЛР2 и ЛР3

## Как проходит запрос

Пользователь получает JWT существующим POST `/auth/login`. Swagger отправляет Bearer-токен в GET `/api/lab2/report` либо `/api/lab3/report`. Gateway проверяет подпись через `current_user`, пересылает параметры и тот же токен во внутренний контейнер. Сервис повторно проверяет JWT и валидирует входные значения. Затем он вызывает функцию выборки и возвращает JSON. При `trace=true` ответ включает время, источник и описание расчёта. Внешний порт есть только у gateway.

## Что делает каждый новый файл

- `app/common/analytics.py`: параметризованные SQL-запросы и сборка результатов. Параметры передаются драйверу отдельно от текста SQL; строки пользователя не подставляются через f-string.
- `app/common/analytical_api.py`: фабрика двух отдельных FastAPI-приложений. Общая форма `/health` и проверка JWT не дублируются. ЛР2 принимает UUID курса, семестр, номер года обучения и год начала учебного года. ЛР3 принимает группу, период и точный тег.
- `app/lab2/main.py` и `app/lab3/main.py`: точки запуска приложений. Разные команды uvicorn запускают разные процессы в отдельных контейнерах из одного образа.
- Новые маршруты в `app/gateway/main.py`: Swagger-документация параметров, проверка токена и проксирование. Сетевой сбой либо не-JSON ответ сервиса превращается в HTTP 502.

## ЛР2 вместимость аудитории

Пример параметров: semester=6, study_year=3, academic_year=2025. Учебный год 2025/2026 соответствует набору 2023 года: `2025 - 3 + 1`. UUID курса берётся из `lecture_courses`.

Одна строка — одно занятие курса. Полные поля курса и занятия возвращаются через `to_jsonb`, включая `tech_requirements`. Состав групп выбирается по специальности курса и году набора. Для обязательного курса считаются все активные студенты; для выборного — только имеющие запись в `student_electives`. `EXISTS` проверяет запись без размножения строк. `count(DISTINCT st.id)` исключает повторный подсчёт студента. Модель вместимости — одно общее занятие для слушателей курса данного года обучения; расписание по отдельным аудиториям этим запросом не оптимизируется.

PostgreSQL выбран потому, что нужен точный состав слушателей и внешние ключи. Эти данные уже структурированы и связаны; полнотекстовый поиск или обход произвольной глубины здесь не нужен.

## ЛР3 часы по группе

Сначала выбирается полная карточка группы. Вторая выборка связывает студентов с обязательными и выбранными курсами, затем оставляет только `lecture_type='lecture'` и точный тег `спецдисциплина кафедры` в массиве тегов занятия. Условие `@>` поддерживается GIN-индексом из ПР3.

План — количество разных занятий расписания в периоде, умноженное на 2. Отменённые занятия исключаются. Посещённые часы — количество этих занятий с `is_present=true`, также умноженное на 2. `LEFT JOIN attendance` сохраняет план, когда отметки нет. Сопоставление недели посещаемости с неделей расписания и границы периода позволяют отсечь лишние партиции. Счётчик DISTINCT защищает отчёт от повторных отметок одного занятия.

Студент и курс без расписания в периоде сохраняются с нулём часов, если у курса есть лекции с заданным тегом. Для отсутствующей группы возвращаются `group=null` и пустой список. Карточка группы и расчёт читаются в одной транзакции REPEATABLE READ READ ONLY, чтобы не смешать состояния при параллельных изменениях.

## Что ещё нужно доказать

Код прошёл синтаксическую проверку и compose config. Расчёт на работающем PostgreSQL, интеграционные проверки JWT, независимая сверка результатов, диаграммы и отчёты ЛР2–3 пока не выполнены. Это текущая реализация, а не протокол успешной сдачи.
