# Защита практической работы №2

**Тема:** CRUD в пяти СУБД на данных «студенты — группы — курсы — посещаемость».
**Что сдаётся:** `Отчёт_Практическая_2.docx` / `.pdf` и каталог `SAD\practice-db\pr2`.

Главная мысль работы, её стоит сказать в первые полминуты:

> «Одни и те же данные учебного процесса я положил в пять СУБД так, как удобно каждой модели.
> В Redis — хеш на студента с ключом-номером зачётки. В MongoDB — группа одним документом
> вместе с составом. В Neo4j — граф, где обязательные курсы висят на группе, а курсы по выбору —
> на каждом студенте. В Elasticsearch — описания курсов с поиском по словоформам. В PostgreSQL —
> журнал посещений, разбитый на недельные партиции. В каждой СУБД сделаны все шесть операций
> задания.»

## 1. Подготовка

1. Запусти стенд ПР №1 (см. `pr1\ЗАЩИТА_ПР1.md`, раздел 1): `docker compose up -d` в каталоге `pr1`.
2. Открой **Git Bash** в каталоге `pr2` (правый клик по папке → *Open Git Bash here*).
3. Проверь, что данные на месте: в `pr2\data` должно быть 11 файлов. Если их нет, выполни
   `python -P make_data.py`.

Перед защитой можно один раз прогнать всё целиком, это займёт около минуты:

```bash
./run_all.sh            # все пять СУБД, вывод — в evidence/*.txt
```

Перед показом хранилища должны быть **пустыми**: `run_all.sh` в конце сам их удаляет.

## 2. Сценарий показа

Удобнее показывать по одной СУБД: команда с `--keep` оставляет данные, потом показываешь их в
веб-интерфейсе, потом удаляешь хранилище.

| СУБД | Показать | Веб-интерфейс | Удалить хранилище после показа |
|---|---|---|---|
| Redis | `./run_all.sh redis --keep`, затем `cat evidence/redis.txt` | http://localhost:8081 → `pr2 (redis:6379:1)` | `docker exec practice01-redis redis-cli -a mypassword -n 1 FLUSHDB` |
| MongoDB | `./run_all.sh mongo --keep` | http://localhost:8082 → `university` → `student_groups` | шаг 6 из `run_all.sh` или `./run_all.sh mongo` |
| Neo4j | `./run_all.sh neo4j --keep` | http://localhost:7474, запрос из раздела 3 | `./run_all.sh neo4j` |
| Elasticsearch | `./run_all.sh es --keep` | Kibana → Dev Tools, запрос из раздела 3 | `curl -X DELETE localhost:9200/lecture_courses` |
| PostgreSQL | `./run_all.sh pg --keep` | pgAdmin → `pr2_attendance` → Tables → attendance → Partitions | `./run_all.sh pg` |

> Важно: если запустить `--keep` дважды подряд, второй запуск споткнётся о уже созданное хранилище
> (`CREATE DATABASE … already exists`, `index already exists`). Сначала удали хранилище, потом
> повторяй.

Что говорить по каждой СУБД — коротко:

- **Redis.** «Хранилище — логическая база №1, она отделена от данных ПР №1 в базе №0. Ключ —
  номер зачётки, значение — хеш с полями. Загрузил 25 студентов через `--pipe` одним пакетом.
  `HSET` по существующему полю меняет значение и возвращает 0 — новых полей не добавилось.
  Удалить запись — `DEL`, удалить хранилище — `FLUSHDB`: чистится только база №1.»
- **MongoDB.** «Группа хранится одним документом с вложенным массивом студентов — это агрегат,
  его читают целиком. Коллекцию создал явно с проверкой схемы `$jsonSchema` и уникальным
  индексом по названию группы. Обновления точечные: `$set`, `$push` вместе с `$inc`, изменение
  одного элемента массива через `arrayFilters`.»
- **Neo4j.** «Курсы по выбору учтены так: обязательные курсы связаны с группой (`STUDIES`),
  выборные — с конкретным студентом (`CHOSE`). Все курсы студента — `UNION` двух путей. Студента
  удаляю `DETACH DELETE`: простой `DELETE` не даст удалить узел, у которого есть связи.»
- **Elasticsearch.** «Индекс с русским анализатором: нижний регистр, стоп-слова, стемминг.
  Поэтому запрос "партиционированием" находит "партиционирование". `_update` меняет часть
  документа, версия растёт.»
- **PostgreSQL.** «Журнал посещений секционирован по неделям: `PARTITION BY RANGE` по понедельнику
  недели, 20 партиций на семестр и партиция по умолчанию. Отметки сформированы случайно: у каждого
  студента своя вероятность посещения, `random() < p`, `setseed` для воспроизводимости. Запрос за
  неделю читает одну партицию — видно в `EXPLAIN`. Неделю можно удалить целиком через
  `DETACH PARTITION` + `DROP TABLE`, без построчного `DELETE`.»

## 4. Если попросят что-то сделать вживую

- **«Найди студента по номеру зачётки»** (Redis):
  `docker exec practice01-redis redis-cli -a mypassword -n 1 --raw HGETALL 23Б0103`
- **«Добавь студента в группу»** (MongoDB, в `mongosh`):
  `db.student_groups.updateOne({name: "БСБО-01-23"}, {$push: {students: {student_card_number: "23Б0130", last_name: "Тестов", first_name: "Тест"}}, $inc: {students_count: 1}})`
- **«Какие курсы выбрали больше всего студентов?»** (Neo4j):
  `MATCH (s:Student)-[:CHOSE]->(c:LectureCourse) RETURN c.name, count(s) AS students ORDER BY students DESC`
- **«Посещаемость студента в процентах»** (PostgreSQL, база `pr2_attendance`):
  `SELECT st.last_name, round(100.0 * avg(a.is_present::int), 1) FROM attendance a JOIN students st ON st.id = a.student_id GROUP BY 1 ORDER BY 2 LIMIT 5;`
- **«Покажи, что запрос за неделю не читает всю таблицу»** (PostgreSQL):
  `EXPLAIN SELECT * FROM attendance WHERE week_start_date = '2026-03-30';` — в плане одна
  партиция `attendance_w2026_03_30`.

## 5. Вопросы и ответы

### Контрольные вопросы методички

**CRUD.** Create, Read, Update, Delete — `INSERT`, `SELECT`, `UPDATE`, `DELETE` в SQL.

**Redis: String, Hash, List, Set, Sorted Set.**
- String — одно значение: кеш страницы, счётчик (`INCR`), сессия.
- Hash — объект с полями: карточка студента.
- List — упорядоченная последовательность: очередь задач, лента событий.
- Set — уникальные элементы без порядка: теги, «кто уже отметился».
- Sorted Set — элементы с весом: рейтинг, топ-10.

**`SET` для существующего ключа.** Значение перезаписывается, и TTL при этом сбрасывается, если
не указать `KEEPTTL`.

**`LPUSH` и `RPUSH`.** Добавляют в начало и в конец списка соответственно. `RPUSH` + `LPOP` дают
очередь FIFO, `LPUSH` + `LPOP` — стек.

**TTL.** Время жизни ключа в секундах (`EXPIRE`, `SET … EX`), по истечении Redis сам удаляет ключ.
Применяется для кеша и сессий.

**`DEL` и `FLUSHDB`.** `DEL` удаляет указанные ключи. `FLUSHDB` удаляет все ключи текущей логической
базы (`FLUSHALL` — всех баз). Поэтому я и держал данные ПР №2 в отдельной базе №1.

**MongoDB: вложенный документ.** Объект внутри документа: у нас `specialty`, `department` и элементы
массива `students` в документе группы.

**`updateOne` и `updateMany`.** Первый меняет первый подходящий документ, второй — все подходящие.

**`$push` и `$set`.** `$push` добавляет элемент в массив, `$set` присваивает значение полю целиком.

**Агрегация.** Конвейер стадий, каждая обрабатывает поток документов: `$match` (фильтр), `$group`
(группировка), `$project` (проекция), `$sort`, `$unwind`, `$lookup` (соединение).

**`upsert: true`.** Если документ по фильтру не найден, `update` создаёт новый.

**Neo4j: узел, связь, свойство.** Узел — сущность с метками (`:Student`). Связь — направленное
типизированное ребро (`:CHOSE`). Свойства — пары ключ-значение и у узлов, и у связей.

**`DELETE` и `DETACH DELETE`.** `DELETE` удаляет узел только без связей, иначе ошибка.
`DETACH DELETE` сначала удаляет все связи узла. Различие важно, чтобы случайно не удалить
связанные данные.

**`MERGE` и `CREATE`.** `CREATE` всегда создаёт новый узел. `MERGE` ищет по шаблону и создаёт
только при отсутствии, повторный запуск не плодит дубликаты. Загрузка у нас на `MERGE`.

**Пример запроса.** Аналог «товары бренда» на наших данных — студенты, выбравшие курс:
`MATCH (s:Student)-[:CHOSE]->(:LectureCourse {name: 'Бизнес-аналитика'}) RETURN s.name`.

**Многие-ко-многим в графе.** Просто связи между узлами, промежуточная таблица не нужна:
студент ↔ курс через `CHOSE`.

**Elasticsearch: маппинг.** Схема индекса: типы полей и анализаторы. Без явного маппинга ES угадает
типы сам и может ошибиться.

**`text` и `keyword`.** `text` анализируется и разбивается на слова, нужен для поиска. `keyword`
хранится целиком, нужен для точного фильтра, сортировки и агрегаций.

**Анализатор.** Три части: символьные фильтры, токенизатор, фильтры токенов. У нас токенизатор
`standard`, фильтры `lowercase`, `russian_stop`, `russian_stemmer`.

**`match` и `match_phrase`.** `match` ищет любые из слов, без учёта порядка. `match_phrase` — слова
подряд в указанном порядке.

**`bool`-запрос.**
- `must` — обязательно и влияет на релевантность.
- `filter` — обязательно, но без оценки релевантности и с кешированием.
- `should` — желательно, повышает оценку.
- `must_not` — исключить.

**PostgreSQL: внешний ключ.** Ограничение «значение столбца есть в первичном ключе другой таблицы»,
обеспечивает ссылочную целостность.

**`DELETE` и `TRUNCATE`.** `DELETE` удаляет строки по условию, построчно, с триггерами.
`TRUNCATE` мгновенно очищает таблицу целиком, без условия.

**Транзакция.** Группа операций «всё или ничего». `BEGIN` — начать, `COMMIT` — зафиксировать,
`ROLLBACK` — отменить.

**JSONB `@>`.** «Содержит»: `WHERE specs @> '{"ram": 16}'`.

**GIN и B-tree.** B-tree — для скалярных значений (равенство, диапазоны, сортировка). GIN —
инвертированный индекс для составных значений: JSONB, массивы, полнотекст.

**hstore и JSONB.** hstore — плоские пары строка-строка. JSONB — вложенные структуры и типы.

**Какая модель подходит.**
- Сессии — Redis.
- Каталог товаров — MongoDB или PostgreSQL с JSONB.
- Социальная сеть — Neo4j.
- Поиск — Elasticsearch.
- Финансы — PostgreSQL, нужен ACID.

**Строгая и гибкая схема.** Строгая — PostgreSQL, отчасти Elasticsearch (тип поля после создания не
меняется). Гибкая — MongoDB, Neo4j, Redis.

**Плюсы и минусы хранения в памяти.** Плюс — скорость. Минусы — объём ограничен ОЗУ, и при сбое
без AOF/RDB данные теряются.

### Вопросы по нашей реализации

**Почему ключ в Redis — просто номер зачётки, без префикса `student:`?**
Так прямо требует задание: «ключом в виде номера зачётной книжки». Пространство имён обеспечено
отдельной логической базой №1.

**Зачем `$jsonSchema`, если MongoDB без схемы?**
Схема гибкая, но не обязана быть бесконтрольной. Валидатор не даст вставить группу без названия
или с названием не того формата. Уникальный индекс превращает название группы в ключ.

**Почему обязательные курсы на группе, а не на каждом студенте?**
Чтобы не дублировать 5 связей × 31 студент. Курс по выбору индивидуален, поэтому он на студенте.
Вместе это и есть «связи группа — студент — курс с учётом курсов по выбору».

**Почему первичный ключ attendance — (`id`, `week_start_date`)?**
В секционированной таблице первичный и уникальные ключи обязаны включать ключ партиционирования:
иначе PostgreSQL не может проверить уникальность в пределах одной партиции.

**Нет внешних ключей у attendance — это ошибка?**
Это решение из методички. С версии 11 PostgreSQL позволяет внешний ключ из секционированной
таблицы, и его можно добавить. Методичка его не ставит: так быстрее массовая вставка и проще
переносить и отсоединять партиции. Целостность здесь гарантирует генератор: отметки строятся
только из существующих студентов и занятий.

**Что такое партиция по умолчанию?**
Куда попадают строки, даты которых не подходят ни под одну неделю, например опечатка в годе. Без
неё такая вставка завершилась бы ошибкой.

**Почему `WITH (FORCE)` при удалении базы?**
К базе был подключён pgAdmin, и обычный `DROP DATABASE` отказал: «is being accessed by other
users». `FORCE` (PostgreSQL 13+) закрывает чужие сеансы.

**Данные случайные — как их повторить?**
`SELECT setseed(0.2026)` перед генерацией. Каждый запуск даёт те же 2544 отметки, это видно по
одинаковым процентам в отчёте и в `evidence/pg.txt`.

**Почему UUID, а не автоинкремент?**
Один и тот же студент получает один id во всех пяти хранилищах: UUID v5 вычисляется из номера
зачётки. Это понадобится в ПР №3, где данные дублируются между хранилищами.
