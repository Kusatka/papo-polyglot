# Защита практической работы №3

**Тема:** проектирование логической и физической структуры данных (polyglot persistence).
**Что сдаётся:** `Отчёт_Практическая_3.docx` / `.pdf` и каталог `SAD\practice-db\pr3`.

Это главная практическая: на её схеме стоят все лабораторные. Преподаватель будет спрашивать
не «что набрано», а «почему так». Ключевая фраза, с которой стоит начать:

> «PostgreSQL — источник истины: в нём все 13 таблиц, все связи и все записи. Остальные четыре
> хранилища держат дубли тех участков, которые удобнее читать в другой модели. Redis — кэш с TTL
> для расписания и карточек студентов. Neo4j — иерархия от университета до курса и связи "группа —
> студент — курс". MongoDB — материалы занятия одним документом. Elasticsearch — поиск по текстам
> с русской морфологией. Журнал посещений в PostgreSQL разбит на недельные партиции. Синхронизация
> дублей делается через CDC в лабораторных 4–6.»


**Обязательно сделай это не раньше чем за час до защиты.** Ключи Redis живут от 30 минут до
2 часов (TTL), и к защите кэш может оказаться пустым. Если это случилось, выполни
`./load_all.sh redis` прямо на защите. Заодно это хорошая демонстрация TTL.

3. Открой отчёт на рисунке 1 (ER-диаграмма) и рисунке 3 (карта размещения).

## 3. Готовые запросы для показа

**PostgreSQL** (`docker exec -it practice01-postgres psql -U admin -d university_system`):

```sql
SELECT start_time, course_name, lecture_type, classroom FROM v_full_schedule
 WHERE group_name = 'БСБО-01-23' AND scheduled_date = '2026-03-16' ORDER BY start_time;

EXPLAIN (COSTS OFF) SELECT count(*) FROM attendance WHERE week_start_date = '2026-03-16';
-- в плане одна партиция attendance_w2026_03_16 — partition pruning

SELECT * FROM v_student_attendance_stats WHERE group_name = 'БСБО-01-23' ORDER BY attendance_percentage LIMIT 5;
```

**Redis** (`docker exec -it practice01-redis redis-cli -a mypassword -n 2 --raw`):
`KEYS schedule:*`, затем `HGETALL <ключ>` и `TTL <ключ>`. После этого — `GET session:student-23b0101`.

**Neo4j Browser** (http://localhost:7474):

```cypher
MATCH p = shortestPath((u:University)-[*]->(c:LectureCourse {name: 'NoSQL и полиглотное хранение'}))
RETURN [n IN nodes(p) | coalesce(n.short_name, n.code, n.name)] AS breadcrumbs
```

Слушатели курсов — основа ЛР №2:

```cypher
MATCH (c:LectureCourse)<-[:HAS_COURSE]-(sp:Specialty)-[:HAS_GROUP]->(:Group)<-[:MEMBER_OF]-(s:Student)
WHERE NOT c.is_elective OR (s)-[:CHOSE]->(c)
RETURN sp.code, c.name, count(DISTINCT s) AS listeners ORDER BY sp.code, listeners DESC
```

**MongoDB** (`mongosh`, база `university_system`):

```javascript
db.lecture_materials.findOne({course_name: "NoSQL и полиглотное хранение", lecture_type: "lab"})
db.lecture_materials.countDocuments({"materials.type": "code_sample", "materials.language": "python"})
```

## 4. Вопросы и ответы

### Контрольные вопросы методички

**1. Что такое polyglot persistence и в чём преимущество?**
Использование нескольких СУБД в одной системе, каждой для того типа данных и запросов, где она
сильнее всего. Плюсы: каждый сценарий обслуживает подходящая модель, хранилища масштабируются
независимо, тяжёлые чтения не нагружают основную базу. Минусы: сложнее эксплуатация, нужна
синхронизация, данные согласованы не мгновенно, а в итоге (eventual consistency).

**2. Почему PostgreSQL — master?**
- ACID-транзакции.
- Ограничения целостности: внешние ключи, `UNIQUE`, `CHECK`.
- Полноценный SQL с JOIN и агрегатами, секционирование.
- Логическая репликация через WAL, на которую опирается CDC.
- Зрелые инструменты резервного копирования.

Источник истины должен гарантировать корректность данных, и это может только реляционная СУБД.

**3. Зачем дублировать в Redis, если всё есть в PostgreSQL?**
Ради скорости и разгрузки. Расписание группы на день читают все студенты группы много раз, а
меняется оно редко. Из памяти Redis ответ приходит за доли миллисекунды по ключу, без соединения
четырёх таблиц. PostgreSQL при этом свободен для записи и отчётов.

**4. Какие данные только в Elasticsearch?**
Полнотекстовый индекс: инвертированный индекс токенов после русского анализатора (основы слов) и
статистика для ранжирования BM25. Этого нет ни в одном другом хранилище. По карте методички тексты
лекций держатся в Elasticsearch как в основном месте. **У нас сознательно иначе:** тексты лежат и в
PostgreSQL (`lecture_materials.content_text`). Тогда индекс всегда можно пересоздать из источника
истины, а CDC имеет откуда брать изменения.

**5. Почему иерархия в Neo4j и какие запросы там лучше, чем JOIN?**
Иерархия — это граф по своей природе. Запрос «все курсы института» в SQL — четыре соединения, в
Neo4j — один шаблон пути. Поиск пути (`shortestPath`) для «хлебных крошек», обход переменной
глубины (`-[*]->`) и вопросы вида «кто связан с кем через N шагов» не дорожают с ростом таблиц:
связь хранится физически, обход идёт по указателям.

**6. Почему материалы лекций в MongoDB, а не строками в PostgreSQL?**
Материалы разнородны. У слайдов есть страницы и размер, у кода — язык, у упражнения — массив
вопросов. В документе у каждого свой набор полей, всё вложено в один агрегат, и страница занятия
читается одним запросом. В реляционной модели это либо таблица с кучей пустых столбцов, либо JSONB
и соединения.

**7. Что такое TTL и почему расписание на час?**
Время жизни ключа: по истечении Redis удаляет ключ сам. Час — компромисс: расписание меняется
редко, поэтому кэш почти всегда попадает. Если расписание всё же изменят, устаревшие данные проживут
не дольше часа. А с CDC кэш обновится сразу.

**8. Как обеспечивается консистентность между PostgreSQL и NoSQL?**
- Запись идёт в одно место, PostgreSQL.
- Изменения захватываются из журнала WAL (CDC: Debezium → Kafka) и применяются в остальных
  хранилищах.
- Ключ везде — один и тот же UUID, поэтому применение изменений идемпотентно (upsert по id).
- Для кэша дополнительно действует TTL.

Это согласованность «в итоге», не мгновенная.

**9. Что будет, если Redis упадёт?**
Система продолжит работать медленнее. Cache-aside при недоступности кэша просто читает PostgreSQL.
Пропадут сессии, пользователям придётся войти заново. Отметки посещаемости будут писаться сразу в
PostgreSQL, без буфера. Источник истины не пострадает.

**10. Логическая и физическая модель — в чём разница?**
Логическая (ER) — сущности, атрибуты, связи и кардинальности, без привязки к СУБД. Физическая —
конкретные таблицы и типы, ключи, индексы, партиции, представления, а также раскладка данных по
хранилищам и их структуры: ключи Redis, узлы Neo4j, документы MongoDB, маппинг Elasticsearch.

**11. Что такое CDC и как он связан с синхронизацией?**
Change Data Capture — захват изменений из журнала транзакций базы и передача их как потока событий.
Debezium читает слот логической репликации PostgreSQL и публикует изменения в топики Kafka.
Коннекторы-приёмники применяют события в Redis, Neo4j, MongoDB и Elasticsearch. Приложению не нужно
писать в пять мест.

**12. Какой паттерн кэширования у расписания?**
Cache-aside (ленивое заполнение): прочитать из Redis → промах → прочитать из PostgreSQL → положить
в Redis с TTL → вернуть. Устаревание — по TTL или по событию CDC.

**13. Почему поиск в Elasticsearch, а не `tsvector` в PostgreSQL?**
У Elasticsearch:
- ранжирование BM25;
- гибкие анализаторы и морфология;
- нечёткий поиск (`fuzziness`);
- подсветка;
- агрегации по метаданным;
- горизонтальное масштабирование.

И он не нагружает основную базу. `tsvector` годится для простых случаев, но по всем этим пунктам
уступает.

**14. Как помогает UUID при нескольких хранилищах?**
UUID уникален без центрального счётчика, поэтому одна сущность имеет один id везде. Это позволяет
связывать данные между хранилищами, делать идемпотентные upsert при синхронизации и не бояться
коллизий. У нас UUID версии 5 вычисляется из естественного ключа (номер зачётки, название курса):
при повторной генерации id не меняются.

### Вопросы по нашей реализации

**Чем ваша схема отличается от методички?**
Добавлено то, что нужно лабораторным:
- `lectures.tech_requirements` — для ЛР №2, «требования к техническим средствам»;
- теги занятий и курсов, в том числе «спецдисциплина кафедры», — для ЛР №3;
- `lecture_courses.department_id` — кафедра, отвечающая за курс;
- `is_elective` и таблица `student_electives` — курсы по выбору из ПР №2;
- представление `v_course_listeners`;
- `CHECK` на понедельник недели в расписании.

**Почему у attendance нет внешних ключей?**
Так в методичке: секционированная таблица с FK медленнее при массовой вставке, а отсоединять и
переносить партиции с ними сложнее. С версии 11 PostgreSQL допускает FK у секционированной таблицы, их
можно добавить. Целостность здесь гарантирует генерация: отметки строятся только по существующим
занятиям и слушателям курса (`v_course_listeners`).

**Зачем `week_start_date` дублируется в schedule?**
Это ключ партиционирования журнала. Без него при вставке отметки пришлось бы вычислять неделю из
даты занятия. `CHECK` гарантирует, что значение всегда равно понедельнику недели.

**Почему 16 партиций с данными из 20?**
Занятия идут 16 недель, с 9 февраля по 29 мая. Партиции созданы на весь семестр с запасом, а
партиция по умолчанию ловит даты вне диапазона.

**Почему у «Проектирования архитектуры ПО» 80 занятий в агрегате MongoDB?**
Курс с таким названием есть у обеих специальностей (у каждой свой UUID и учебный план), а агрегация
группирует по названию: 40 + 40. В графе запрос слушателей группирует по специальности, поэтому
там они разделены: 31 и 46.

**Что слушает студент?**
Обязательные курсы — все курсы специальности его группы (`is_elective = false`). Курсы по выбору —
только отмеченные в `student_electives` / связью `CHOSE`.
