# План и речь для защиты ПР 1–3 и ЛР 1

Это краткий сценарий для устной защиты. Не зачитывай его буквально: открывай код, выполняй короткие команды и поясняй, почему выбран именно такой способ хранения.

## Накануне и за 10 минут до начала

1. Запусти Docker Desktop и дождись `Engine running`.
2. В `practice-db\pr1` выполни `docker compose up -d`, затем `docker compose ps`.
3. В Git Bash из `practice-db\pr3` выполни `./load_all.sh`; это восстанавливает одинаковые данные во всех хранилищах.
4. В `practice-db\lab1` выполни `docker compose up -d --build`.
5. Проверь лабораторную: `python tests\verify.py масштабирование 2026-02-09 2026-04-19`.
6. Открой заранее отчёты, `docker-compose.yml`, Swagger: `http://localhost:8000/docs`, а также pgAdmin, Neo4j Browser, Redis Commander и Kibana.

Не выполняй `docker compose down -v`: он удаляет тома и данные.

## Общий порядок защиты

На каждую работу держи один и тот же каркас:

1. Цель и предметная область — 20–30 секунд.
2. Покажи источник: compose-файл, схему или код.
3. Выполни один короткий живой запрос с результатом.
4. Объясни техническое решение и альтернативу.
5. Покажи, чем подтверждена корректность: healthcheck, тест, скриншот или независимая сверка.

## Практическая работа 1 — стенд СУБД

### Что показать

1. `practice-db\pr1\docker-compose.yml`.
2. `docker compose ps` — Redis, MongoDB, Neo4j, Elasticsearch, PostgreSQL и их веб-интерфейсы должны быть healthy/running.
3. По одному `PING`/health-запросу к пяти СУБД.
4. Именованные тома: `docker volume ls --filter name=practice01`.
5. Папку `pr1\logs` и один файл журнала.

### Речь

> В этой работе я развернул единый Docker Compose-стенд из пяти разных СУБД. PostgreSQL — реляционное транзакционное хранилище, MongoDB — документы, Redis — key-value в памяти, Neo4j — граф, Elasticsearch — полнотекстовый индекс. У каждой службы есть healthcheck, а веб-интерфейс зависит от статуса healthy, поэтому доступность проверяется не только фактом запуска контейнера. Данные вынесены в именованные Docker volumes: пересоздание контейнера их не удаляет. Логи СУБД смонтированы отдельно, поэтому их можно анализировать с хоста. Это даёт воспроизводимый стенд для следующих работ.

### Что помнить

- `depends_on` без `condition: service_healthy` задаёт порядок, но не гарантирует готовность приложения.
- `stop` оставляет контейнеры; `down` удаляет контейнеры и сеть; `down -v` удаляет ещё и volumes.
- Redis: скорость за счёт RAM, сохранность — AOF/RDB. Elasticsearch и Neo4j требуют явно ограничивать JVM heap.

## Практическая работа 2 — CRUD

### Что показать

1. `practice-db\pr2\run_all.sh` и таблицу CRUD из отчёта.
2. Запусти, если времени мало, один полный сценарий: `./run_all.sh redis --keep` либо `./run_all.sh pg --keep` в Git Bash.
3. Для PostgreSQL покажи `PARTITION BY RANGE (week_start_date)` в `data\pg_schema.sql`.
4. Скажи, что скрипт последовательно демонстрирует создание хранилища, запись, чтение по ключу, изменение, удаление записи и удаление хранилища для каждой из пяти СУБД.

### Речь

> Во второй работе я выполнил полный CRUD для тех же пяти типов хранилищ, но на общей предметной области учебного процесса. Представление данных соответствует модели СУБД: в Redis студент — Hash с ключом номера зачётной книжки; в MongoDB группа — документ со вложенным составом; в Neo4j связи показывают группу, студента и выбранные курсы; Elasticsearch хранит полнотекстовые описания курсов; PostgreSQL хранит расписание и посещаемость. Для PostgreSQL журнал посещаемости секционирован по неделям, поэтому аналитический запрос по периоду читает только нужные партиции. Скрипты воспроизводят все шесть требуемых действий, а не только конечное состояние данных.

### Что помнить

- CRUD: Create, Read, Update, Delete; в SQL — `INSERT`, `SELECT`, `UPDATE`, `DELETE`.
- MongoDB: `$set` заменяет/задаёт поле, `$push` добавляет элемент массива; `upsert` создаёт документ, если его нет.
- Neo4j: `CREATE` всегда создаёт, `MERGE` ищет шаблон или создаёт; `DETACH DELETE` нужен для узла со связями.
- Elasticsearch: `text` анализируется для поиска, `keyword` — точное значение, сортировка и агрегации.

## Практическая работа 3 — polyglot persistence

### Что показать

1. ER-диаграмму `pr3\diagrams\er.png`.
2. `pr3\schema.sql`: таблицы, внешние ключи, индексы и недельное партиционирование attendance.
3. Карту `pr3\diagrams\map.png` и схему потоков `flows.png`.
4. По одному примеру: Redis-ключ, запрос Cypher, MongoDB-документ и Elasticsearch mapping/query.
5. `pr3\load_all.sh` как воспроизводимую загрузку всех пяти хранилищ.

### Речь

> В третьей работе я спроектировал модель учебного процесса по принципу polyglot persistence. PostgreSQL — source of truth: в нём полная нормализованная схема, внешние ключи и транзакционная посещаемость, разбитая на недельные партиции. Из него формируются специализированные проекции: Redis хранит часто читаемые карточки и расписание с TTL, Neo4j — иерархию и связи курсов, MongoDB — составные материалы занятия, Elasticsearch — индекс текстов лекций с русским анализатором. Это не пять независимых источников истины: основная запись идёт в PostgreSQL, а синхронизация дублей в дальнейшем предполагается через CDC. Выбор сделан по типу нагрузки: транзакции, кэш, обход графа, документ-агрегат и поиск соответственно.

### Что помнить

- Логическая модель отвечает на вопрос «какие сущности и связи», физическая — «какие таблицы, типы, индексы и партиции».
- TTL ограничивает устаревание кэша; при недоступности Redis приложение читает PostgreSQL медленнее, но корректно.
- CDC читает изменения журнала транзакций и обновляет производные хранилища.
- UUID удобны для согласованной идентификации одной сущности в разных СУБД.

## Лабораторная работа 1 — аналитический API

### Что показать

1. C4 (`lab1\diagrams\c4_context.png`, `c4_container.png`) и DFD (`dfd_context.png`, `dfd_level1.png`).
2. `lab1\docker-compose.yml`: наружу опубликован только gateway:8000; сервис лабораторной доступен лишь во внутренней сети.
3. Swagger UI: `POST /auth/login`, затем защищённый `GET /api/lab1/report`.
4. Отчёт для термина «масштабирование» и периода `2026-02-09`—`2026-04-19`; включи `trace=true`.
5. `python tests\verify.py масштабирование 2026-02-09 2026-04-19`.

### Речь

> Лабораторная реализует защищённый аналитический запрос: вернуть десять студентов с минимальной посещаемостью занятий, содержащих заданный термин, за выбранный период. Пользователь получает JWT у API Gateway, шлюз проверяет токен и передаёт запрос внутреннему сервису; сервис проверяет токен повторно. Поиск лекций выполняется в Elasticsearch, потому что нужен русскоязычный полнотекстовый поиск и подсветка. PostgreSQL рассчитывает посещаемость по найденным занятиям и отсекает лишние недельные партиции. Redis отдаёт карточки студентов по cache-aside, а промахи кэша дочитываются из PostgreSQL. В ответе есть trace с временем и результатом каждого шага, а независимый SQL-тест сверяет итоговую десятку.

### Что помнить

- JWT подписан: полезная нагрузка читаема, но её нельзя изменить без секрета. Здесь HS256; для внешних независимых сервисов уместнее RS256.
- `search_after` нужен, чтобы не потерять результаты за пределами одной страницы Elasticsearch.
- Процент: посещённые найденные лекции / все найденные лекции группы в периоде × 100.
- Cache-aside: сначала кэш, затем источник истины при промахе, после чего кэш обновляется с TTL.

## Если зададут неудобный вопрос

Не угадывай. Называй границу решения: «В учебном стенде это сделано так, а в production я бы добавил …». Хорошие продолжения: TLS, секреты вместо `.env`, роли и авторизация, refresh tokens/отзыв JWT, мониторинг, CDC, retry и обработка недоступности хранилища.
