# Практическая №3 — полиглотная модель хранения

**Группа:** БСБО-01-23. **Кафедра/специальность:** Бизнес-информатика (38.03.05).

Идея *polyglot persistence*: одни и те же предметные данные (кафедра →
специальность → группа → студент → курс → лекция → запись на курс →
посещаемость) раскладываются по пяти хранилищам так, чтобы **каждый
аналитический запрос обслуживался движком, чьи характеристики оптимальны
именно для него**. Канонический источник истины — реляционная схема в
PostgreSQL (`practical3/schema.sql`); остальные четыре хранилища — это
специализированные проекции этой модели.

## Каноническая реляционная модель (PostgreSQL)

```
department 1───* specialty 1───* study_group 1───* student
                                   course *───* student        (enrollment, is_elective)
                                   course 1───* lecture
                                   course *───* tag             (course_tag)
                                   attendance(student, lecture, course, visit_date, attended)
                                              └ PARTITION BY RANGE(visit_date)  — по неделям
```

Связи и кардинальности — в ER-диаграмме отчёта (`reports/`). Ниже —
распределение по пяти видам представления и **обоснование** каждого выбора.

---

## 1. Redis — ключ-значение → справочник студентов

**Что храним:** хэш по каждому студенту, ключ = номер зачётной книжки
(`student:{record_book_no}`), плюс индекс группы (`group:{code}` → SET зачёток).

**Почему Redis:** обогащение «полной информацией о студенте» в лаб. №1 — это
точечный доступ по известному ключу (зачётке). Redis даёт O(1)-чтение из
памяти; нет смысла джойнить ради карточки студента. Ключ = зачётка
соответствует прямому требованию практ. №2.

**Характеристика, которую используем:** in-memory key-value, минимальная
латентность точечного `GET/HGETALL`.

## 2. MongoDB — документ-композиция → состав группы

**Что храним:** один документ на группу (`groups`), с вложенным массивом
студентов и их курсов (денормализованная иерархия группа → студенты → курсы).

**Почему MongoDB:** «состав группы» — естественно цельный агрегат, который
читается/показывается целиком. Документная модель убирает джойны и отдаёт
готовую иерархию одним запросом. Удобна как материализованное представление
для UI и как источник обогащения, когда нужна вся группа сразу.

**Характеристика:** агрегат-ориентированное хранение, schema-flexible,
вложенные документы вместо джойнов.

## 3. Neo4j — типизированные связи → граф учёбы (вкл. курсы по выбору)

**Что храним:** узлы `Specialty, Group, Student, Course, Lecture` и рёбра
`(:Student)-[:IN_GROUP]->(:Group)-[:OF_SPECIALTY]->(:Specialty)`,
`(:Student)-[:ENROLLED {elective}]->(:Course)`,
`(:Course)-[:HAS_LECTURE]->(:Lecture)`.

**Почему Neo4j:** курсы по выбору и связи «специальность ↔ курс ↔ студент»
образуют граф многие-ко-многим. Графовые обходы (кто на какие выборные курсы
записан, общие курсы между студентами/группами, какие курсы образуют граф
зависимостей) на реляционке выливаются в многократные JOIN/рекурсию, а в Neo4j
выражаются коротким Cypher по рёбрам. Для лаб. №2 граф даёт число слушателей
курса обходом `(:Course)<-[:ENROLLED]-(:Student)`.

**Характеристика:** index-free adjacency, дешёвые обходы переменной глубины.

## 4. ElasticSearch — полнотекст + метаданные → описания курсов и лекций

**Что храним:** индекс `lectures` — документ на лекцию с полями
`content`, `topic` (полнотекст с русским анализатором) и метаданными-фильтрами
`course_id, course_code, course_title, study_year, semester, academic_year,
tech_requirements, tags, planned_date`.

**Почему ElasticSearch:** оба лабораторных запроса начинаются с поиска по
**тексту** лекций/курса: лаб. №1 — «лекции, содержащие заданный термин или
фразу»; лаб. №2 — отбор по описанию и требованиям к техническим средствам.
Инвертированный индекс с морфологией (стемминг русского) и `match_phrase`
делает это на порядок эффективнее, чем `LIKE '%...%'` в SQL. Метаданные в том
же документе позволяют сразу сузить выборку (период, семестр, год).

**Характеристика:** инвертированный индекс, полнотекст с анализаторами,
фильтры по метаданным в одном запросе.

## 5. PostgreSQL — транзакционные данные + партиционирование → посещаемость

**Что храним:** таблица `attendance`, **партиционированная по неделе**
(`PARTITION BY RANGE(visit_date)`, по партиции на ISO-неделю). Плюс вся
нормализованная схема как источник истины.

**Почему PostgreSQL:** расчёт процента посещения за период — это агрегат
(`AVG(attended::int)`) над большим объёмом фактов с фильтром по диапазону дат.
Партиционирование по неделе обеспечивает **partition pruning**: при фильтре
по периоду планировщик читает только релевантные недельные партиции, а не всю
историю. ACID-транзакции и оконные функции — родная среда для таких выборок.

**Характеристика:** реляционные агрегаты, секционирование по диапазону дат,
строгая согласованность.

## Как это обслуживает лабораторные запросы

| Запрос | Полнотекст | Агрегация/факты | Граф | Обогащение |
|--------|-----------|------------------|------|------------|
| **Лаб.1** — 10 студентов с min % посещения лекций по термину за период | ES: лекции с термином | PostgreSQL: % посещения по партициям недель | — | Redis/Mongo: карточка студента |
| **Лаб.2** — объём аудитории для курса за семестр/год + тех. средства | ES: курс/лекции + tech_requirements + фильтр семестр/год | PostgreSQL/Neo4j: число слушателей (enrollment) | Neo4j: обход `ENROLLED` | Mongo: состав |

Объединение результатов разных движков выполняется **на уровне сервиса**
(федеративный запрос), т.к. между ES и PostgreSQL нет нативного JOIN — это и
есть архитектурный смысл полиглотного хранения.
